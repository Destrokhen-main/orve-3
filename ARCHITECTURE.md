# Orve — архитектура

Самодостаточное описание проекта: его можно целиком отдать модели как контекст.

Orve — фронтенд-фреймворк на сигналах с JSX. Без виртуального DOM в привычном
смысле: JSX-узел — это плоский объект-описание, а сопоставление с DOM делает
один общий реконсилятор. Зависимостей в рантайме нет.

---

## 1. Ядро реактивности (`src/core/reactive`)

Модель Vue-подобная: источник хранит набор подписчиков, эффект хранит обратные
ссылки на наборы, в которых состоит. Это даёт точечную отписку.

### Публичный API

```ts
state<T>(value, options?) -> State<T>
  .value        // чтение с подпиской, запись через сеттер
  .get()        // то же чтение, но вызовом: get(): T
  .get(fn)      // чтение с преобразованием: get<R>(fn: (v: T) => R): R
  .peek()       // чтение без подписки
  .set(v)       // значение либо апдейтер: set(v => v + 1)
  StateOptions.equals: false | ((old, next) => boolean)   // по умолчанию Object.is

reactive<T extends object>(target) -> T   // глубокий прокси: подписка по свойствам
  toRaw(value)      // исходный объект из-под прокси
  markRaw(obj)      // никогда не оборачивать
  isReactive(value)
  // объекты, массивы, Map/Set/WeakMap/WeakSet; Date/RegExp/DOM/frozen — как есть

computed<T>(fn, options?) -> Computed<T>
  .value        // ленивое вычисление: пересчёт на чтении, если помечен грязным
  .peek() / .stop()
  ComputedOptions.deps: DepSource[]  // явные зависимости вместо авто-трекинга
  // DepSource = State | Computed | объект от reactive() (обход вглубь) | геттер

watch(cb, deps, options?) -> Watch
  .un() / .pause() / .resume()       // изменения во время паузы догоняются одним вызовом
  OptionsWatch.immediate

effect(fn, options?) -> Effect        // выполняется сразу, перезапускается при изменениях
untrack(fn)                           // прочитать без подписки
effectScope(detached?) -> EffectScope // .run(fn) / .stop(); владеет эффектами
onScopeDispose(fn)                    // колбэк на остановку текущей области
nextTick(fn?) -> Promise              // резолвится после разбора очереди
flushSync()                           // синхронно разобрать очередь
```

### `State.get` — частный случай `.value`

`get()` — то же реактивное чтение, что и `.value`, только вызовом. Смысл
перегрузки с аргументом в том, чтобы преобразование входных данных жило прямо в
точке чтения:

```ts
const status = state<"foo" | "baz">("foo");

status.get();                       // "foo" | "baz"
status.get((v) => v === "foo");     // boolean
status.get((v) => (v === "foo" ? bar : qwer));   // typeof bar | typeof qwer
```

- Тип результата выводится из `fn` (`get<R>(fn: (v: T) => R): R`), а не
  схлопывается в `any` — в TS цепочка `status.get(...)` остаётся типизированной.
- Подписка встаёт на само состояние, а не на результат: `fn` — чистое
  преобразование прочитанного, вызывается синхронно и своих зависимостей не
  заводит.
- `fn` обязан вернуть значение на всех ветках — иначе `R` выведется с
  `undefined`, и это увидит компилятор.
- Кеширования нет: `get(fn)` пересчитывает `fn` на каждом чтении. Когда нужен
  ленивый пересчёт и разделяемый результат — это `computed`, а не `get`.

### Инварианты, на которые всё опирается

1. **Стек активных эффектов** (`core/stack.ts`), не одна ячейка. Вложенный
   эффект или computed внутри рендера не ломает трекинг внешнего.
2. **Точечная отписка.** `Effect.deps` — массив наборов, в которых эффект
   состоит; `cleanup()` удаляет только себя. Соседние подписки не задеваются.
3. **Пере-трекинг на каждом прогоне.** Перед запуском эффекта зависимости
   сбрасываются, поэтому ветвления (`if (flag) a.value else b.value`) точны.
4. **Дедупликация в `track`.** Три чтения одного сигнала = одна подписка.
5. **Батчинг через микротаск** (`core/scheduler.ts`). Очередь забирается
   целиком перед проходом, добавленное во время выполнения идёт следующим
   проходом. Ограничитель в 1000 проходов ловит бесконечные циклы.
6. **Computed ленивый.** Изменение зависимости синхронно помечает грязным и
   пробрасывает инвалидацию дальше; пересчёт — только при чтении.
7. **`EffectScope` — владение.** Всё, созданное внутри `scope.run()`,
   останавливается вместе с областью. Вложенные области умирают с родителем.
   Текущая область спрятана за `ScopeHost`: `getCurrentScope()` спрашивают
   только когда есть что положить, поэтому владельцы могут создавать области
   лениво (`runWithScopeHost`).
8. **`reactive()` — тот же трекинг, но по ключам** (`reactive/`). `State`
   трекает себя под одним ключом `VALUE_KEY`; прокси трекает `target[key]` на
   `get`/`has`/`ownKeys` и триггерит на `set`/`delete`. Отдельный `ITERATE_KEY`
   отвечает за состав ключей (`for...in`, `Object.keys`, `size`, итерация).
   Обёртки лениво создаются на чтении и кешируются в `WeakMap`, поэтому
   `store.nested === store.nested`. В сырое дерево кладутся сырые значения:
   прокси в состоянии не накапливаются. Мутирующие методы массива вызываются
   внутри `untrack`, иначе `arr.push()` в эффекте подписал бы его на `length`,
   который он же и меняет.

Файлы: `core/index.ts` (track/trigger, `effect`), `core/effect.ts`,
`core/scheduler.ts`, `core/stack.ts`, `core/scope.ts`, `state/`, `computed/`,
`watch/`, `reactive/` (`index.ts` — базовые трапы, `collections.ts` — Map/Set,
`shared.ts` — символы, кеш, `toRaw`/`markRaw`).

## 2. Модель компонента

Компонент всегда возвращает функцию:

```ts
type ComponentFn<P> = (props: P) => Render;
type Render = () => Child;
```

`setup` (тело компонента) выполняется **один раз** внутри собственной
`EffectScope`. Размонтирование = `scope.stop()`.

Из «один раз» следует главное практическое правило фреймворка:
**пропсы нельзя деструктурировать** — ни `({ text }) =>`, ни `const { text } =
props`. Подробности и примеры ниже, в разделе про пропсы.

### Хуки жизненного цикла

Вызываются в `setup`, работают в обоих режимах:

```tsx
const Widget = () => {
  onMounted(() => {/* узлы уже в документе, можно мерить и вешать слушателей */});
  onBeforeUnmounted(() => {/* DOM ещё на месте, эффекты живы */});
  onUnmounted(() => {/* узлы сняты, область эффектов остановлена */});

  return () => <div />;
};
```

- Регистрация идёт через стек «текущего инстанса» (`component/lifecycle.ts`),
  который выставлен только на время вызова `setup`. Вне его — предупреждение в
  консоль, потому что колбэк уже некому вызвать.
- `onMounted` **отложен**: элемент вставляется в родителя последним действием
  своего монтирования, поэтому в момент готовности вложенного компонента его
  узлов ещё нет в документе. Колбэки копятся и разбираются, когда завершилось
  самое внешнее монтирование — порядок получается снизу вверх, дети раньше
  родителей, как в Vue.
- Обновление пропсов `setup` не перезапускает, поэтому `onMounted` срабатывает
  ровно один раз за жизнь инстанса.
- `unmount` идемпотентен: повторный вызов хуки не продублирует.
- Исключение в хуке логируется и не роняет монтирование соседей.

Есть два режима потребления возвращённой функции.

### Базовый (по умолчанию)

`render` обёрнут в эффект: при изменении прочитанной реактивности он
перевызывается целиком, новое дерево диффится со старым, в DOM уходит разница.

```tsx
const Counter = () => {
  const count = state(0);
  return () => <span>{count.value}</span>;   // ЗНАЧЕНИЕ
};
```

- В слотах пишутся значения (`count.value`).
- Условия и списки — обычный JS (`&&`, `map`), структура дерева свободная.
- Списки требуют `key`, иначе узлы сопоставляются по позиции.

> **⚠️ Сигнал в слоте без `single`.**
> Если передать сигнал напрямую (`{count}` вместо `{count.value}`), фреймворк
> выведет предупреждение `[orve]` в консоль и прочитает текущее значение как
> fallback. Реактивная подписка при этом встаёт в render-эффект компонента —
> компонент будет обновляться корректно, но это сигнал об ошибке: в базовом
> режиме слот должен содержать значение, а не сигнал.

### Сингл (маркер `defineOptions`)

`render` вызывается **ровно один раз**. Реактивность живёт только там, куда в
дерево попал сам сигнал или тонк.

```tsx
const Counter = () => {
  defineOptions({ single: true });
  const count = state(0);
  return () => <span>{count}</span>;          // СИГНАЛ
};
```

- В слотах — сигнал `{count}` или тонк `{() => expr}`. `{count.value}`
  вычислится один раз и застынет.
- Структура дерева статична: обычный `if`/`map` отработает единожды.
  Динамика — только через `<If>` / `<For>` / `<Component>`.

### Правила JSX (общие)

| Что | Как читается |
|---|---|
| `{"текст"}`, `{42}`, `{null}` | статический текст |
| `{signal}` | реактивный слот — **только в сингл**; в базовом выдаёт `[orve]` warn и читается как значение |
| `{() => expr}` | реактивный слот-тонк — **только в сингл**; в базовом выдаёт `[orve]` warn и вычисляется один раз |
| `class={signal}`, `class={() => …}` | реактивный атрибут |
| `onClick={fn}` | **всегда обработчик**, никогда не тонк |
| `onClickCapture={fn}` | обработчик в фазе перехвата |
| `onClick={[fn, { once: true }]}` | обработчик с опциями слушателя |
| `ref={fn}` / `ref={signal}` | доступ к DOM-узлу; при размонтировании приходит `null` |
| `key={…}` | идентичность узла для реконсилятора |
| `value={signal}` в пропсах компонента | разворачивается: ребёнок читает `props.value` как значение |

### Пропсы — то, что склеивает режимы

`ReactiveProps` строит объект с геттерами поверх ячеек `State`:

- базовый родитель при перерисовке **пишет в ячейку**, а не пересоздаёт ребёнка;
- сингл-ребёнок читает `props.x` внутри своих слотов и обновляется точечно;
- проп-сигнал (`items={items}`) разворачивается — внутри виден обычный `string[]`.

Типы: снаружи JSX принимает `MaybeReactive<P[K]>` (через
`JSX.LibraryManagedAttributes`), внутри компонента тип остаётся значением.

Запись в ячейку идёт через апдейтер — `cell.set(() => value)`. Иначе проп,
который сам является функцией (компонент в `is`, колбэк `onPick`), был бы
выполнен: `State.set` трактует переданную функцию как апдейтер.

### ⚠️ Пропсы нельзя разбирать — ни в сигнатуре, ни в теле

Самая частая ошибка на этом фреймворке. Тело компонента — это `setup`, оно
выполняется **один раз**. Любая деструктуризация читает геттер в этот
единственный момент и кладёт результат в обычную переменную: реактивное чтение
уже случилось, подписываться дальше не на что, значение застывает навсегда.

```tsx
// ❌ text прочитан один раз в setup — обновления не придут никогда
const Badge = ({ text }: { text: string }) => {
  return () => <div>{text}</div>;
};

// ❌ то же самое, просто строкой ниже
const Badge = (props: { text: string }) => {
  const { text } = props;
  return () => <div>{text}</div>;
};

// ✅ читаем в момент рендера — геттер трогает ячейку, эффект подписывается
const Badge = (props: { text: string }) => {
  return () => <div>{props.text}</div>;
};
```

Передача сигнала вместо значения (`<Badge text={signal} />`) от этого **не
спасает**: `ReactiveProps` разворачивает сигнал внутри геттера, поэтому
`{ text }` всё равно заберёт голое значение.

Правило действует одинаково в обоих режимах и по всей глубине: `props.a.b`
читать можно, `const { a } = props` — нельзя. То же касается `Object.assign`,
spread (`{ ...props }`) и передачи `props` в функции, которые разбирают его
внутри.

Обойти это можно только компилятором (как деструктуризация `defineProps` во
Vue) — макросом, переписывающим `text` обратно в `props.text`. Мы сознательно
живём без своего трансформа, так что здесь — соглашение, а не проверка.

**Функции в пропсах компонента не вызываются автоматически** — иначе сломались
бы колбэки (`For`-children, `ref`, обработчики). Компонент, который допускает
тонк, разворачивает его сам через `resolve()`: так сделаны `If.when` и
`For.each`. У интринсик-тегов правило обратное: там функция в слоте или
атрибуте — это тонк, а обработчик отличается префиксом `on`.

### `forwardProps` — единственный законный способ разобрать пропсы

```ts
forwardProps(props: Props, skip: (keyof Props)[] = []) -> Props
```

Плоская копия объекта пропсов: перебирает ключи `for…in`, пропускает
перечисленные в `skip`, кладёт остальные в новый объект. Нужна там, где
пропсы уезжают дальше — в другой компонент, в тег, в `jsx(...)` — и часть из
них служебная.

```tsx
// src/components/component-orve/Component.ts — `is` остаётся снаружи
const forwarded = forwardProps(props, ["is"]);
```

```tsx
// playground/cases/BaseRouter/router.tsx — RouterLink отдаёт всё вниз
return () => {
  const component = currentRoute.value?.component;
  if (!component) return null;
  return jsx(component as ComponentFn<any>, forwardProps(props));
};
```

Это ровно тот случай, о котором говорит запрет из предыдущего раздела:
`forwardProps` **читает геттеры** `ReactiveProps` и превращает их в обычные
значения. Отсюда правило вызова:

- **Только внутри render или тонка**, никогда в `setup`. В `setup` копия
  снимется один раз и застынет — то же самое, что `const { … } = props`.
- Вызванный в render, он подписывает текущий эффект **на все** скопированные
  пропсы (кроме `skip`): изменился любой из них — родительский render или тонк
  перевызывается, и копия пересобирается заново.
- Копия плоская и по значению. Дальше ребёнок получает обычные пропсы, а его
  `ReactiveProps` уже сам заведёт под них ячейки — `setup` ребёнка от этого не
  перезапускается.
- `skip` полезен и как способ сузить подписку: пропущенный ключ не читается,
  значит и зависимости от него не появится.

## 3. Контекст компонента (`src/instance/context`)

### provide / inject

Механизм передачи произвольных значений от родителя всем потомкам без явного
пробрасывания через пропсы. Не реактивный: передаётся обычный объект.
Регистрация происходит в `setup`, доступ — тоже в `setup` любого потомка.

```tsx
const key = Symbol('theme');

const Parent = () => {
  provide(key, { color: 'red' });
  return () => <Child />;
};

const Child = () => {
  const theme = inject<{ color: string }>(key);
  return () => <div style={{ color: theme?.color }} />;
};
```

- `provide(key, value)` — записывает значение в контекст текущего компонента.
  Ключ — `string` или `symbol`.
- `inject<T>(key, defaultValue?)` — ищет значение вверх по дереву контекстов:
  от текущего компонента к родителю, прадеду и т.д. Возвращает первое найденное
  или `defaultValue`, если ничего не нашлось.
- Оба вызова допустимы только в `setup`. Вне него — предупреждение `[orve]`
  в консоль, `provide` игнорируется, `inject` возвращает `defaultValue`.
- Контекстов может быть сколько угодно: несколько `provide` с разными ключами
  внутри одного компонента — норма.

### ContextType и стек контекстов

Каждый [`ComponentView`](../src/components/component/view.ts) создаёт
собственный `ContextType` при монтировании:

```ts
type ContextType = {
  provide: Record<string | symbol, unknown>;  // значения, объявленные provide()
  options: ComponentOptions;                   // настройки defineOptions()
  parent: ContextType | null;                 // ссылка на контекст родителя
};
```

Стек в [`context.ts`](../src/instance/context/context.ts) работает по той же
схеме, что и стек хуков в [`lifecycle.ts`](../src/components/component/lifecycle.ts):

| Функция | Назначение |
|---|---|
| `createContext(parent)` | создать новый контекст с указателем на родителя |
| `pushContext(ctx)` | сделать контекст текущим (вход в setup) |
| `popContext()` | снять контекст (выход из setup) |
| `getCurrentContext()` | прочитать текущий контекст |
| `withContext(ctx, fn)` | выполнить `fn` в контексте `ctx` |

В `ComponentView.mount`:
1. Захватывается `parentCtx = getCurrentContext()` — контекст родителя.
2. Создаётся `myCtx = createContext(parentCtx)`.
3. На время `setup` выставляется `pushContext(myCtx)` / `popContext()`.
4. Все вызовы `applyTree` оборачиваются в `withContext(myCtx, ...)`,
   чтобы при каждом перерендере дочерние компоненты находили цепочку провайдеров.

### defineOptions

`defineOptions(options)` пишет в `getCurrentContext().options`.
Тот же стек, тот же механизм — никакого отдельного глобального состояния.
В будущем сюда можно добавить любые настройки уровня компонента.

## 4. Плагины (`src/instance/plugins`)

Плагин — это способ положить что-то (роутер, стор, i18n) в один общий объект,
который виден из `setup` любого компонента. В отличие от `provide/inject`
плагины не привязаны к месту в дереве: они ставятся на инстанс до монтирования
и доступны везде.

```ts
const instance = createInstance()
  .use(routerPlugin, { base: "/app" })
  .use((cx, api) => {
    cx.$store = createStore();
    api.onUnmounted(() => cx.$store.dispose());
  })
  .rootComponent(App)
  .mountRoot("#app");
```

```tsx
const Page = () => {
  const router = usePlugin("$router");   // либо usePlugins().$router
  return () => <a onClick={() => router.push("/next")}>дальше</a>;
};
```

### Форма плагина

Плагин — объект `{ name?, setup }` либо просто функция `setup`:

```ts
type PluginSetup<O> = (context: PluginContext, api: PluginApi<O>) => PluginCleanup | void;
type OrvePluginType<O> = { name?: string; setup: PluginSetup<O> };
type OrvePluginInput<O> = OrvePluginType<O> | PluginSetup<O>;
```

`setup` вызывается **один раз**, в момент `use()`, синхронно. Первый аргумент —
сам контекст плагинов, его можно мутировать напрямую (`cx.$router = …`). Второй —
`PluginApi`:

| Член | Назначение |
|---|---|
| `name` | имя плагина: из `plugin.name` либо сгенерированное `orve-plugin-N` |
| `options` | второй аргумент `use(plugin, options)` |
| `instance` | сам инстанс — можно доставить зависимый плагин через `api.instance.use(…)` |
| `provide(key, value)` | типобезопасная альтернатива прямой мутации контекста |
| `has(name)` | установлен ли плагин с таким именем — для зависимостей между плагинами |
| `onMounted(fn)` | после монтирования корневого компонента |
| `onUnmounted(fn)` | при `instance.unmount()` |

Возвращённая из `setup` функция — тот же `onUnmounted`, только короче:

```ts
const timerPlugin: OrvePluginType = {
  name: "timer",
  setup(cx) {
    const id = setInterval(tick, 1000);
    cx.$timer = { stop: () => clearInterval(id) };
    return () => clearInterval(id);        // cleanup
  },
};
```

### Реестр (`registry.ts`)

`OrveInstance` не работает с плагинами напрямую — этим занимается
`PluginRegistry`, по одному на инстанс. Он держит три вещи, которых нет в самом
плагине:

1. **Порядок.** Плагины ставятся в порядке `use()`, и каждый следующий видит
   контекст всех предыдущих. Так один плагин строится поверх другого:
   `cx.$b = cx.$a + 1`.
2. **Дедупликация.** Один и тот же плагин (по ссылке) или одно и то же имя
   ставятся один раз; повтор — предупреждение `[orve]` и пропуск. Анонимные
   плагины получают уникальное сгенерированное имя, поэтому под дедупликацию
   по имени не попадают.
3. **Жизненный цикл.** `mountRoot()` вызывает `registry.mount()`, `unmount()` —
   `registry.unmount()`.

### Инварианты

- **Ошибка в `setup` не роняет инстанс и не оставляет мусора.** `setup` работает
  с копией контекста; в общий контекст она сливается только при успешном
  завершении. Упавший плагин логируется как `[PLUGIN] "имя" …` и просто не
  ставится — частичных изменений в контексте не остаётся.
- **Контекст пересоздаётся, а не мутируется.** Каждый `use()` даёт новый объект.
  Корневой `ContextType` захватывает ссылку в момент `mountRoot()`, поэтому
  плагин, поставленный после монтирования, в уже созданных компонентах не
  появится — но в самом инстансе он есть и свой `onMounted` получит сразу.
- **Порядок гашения обратный установке.** `onUnmounted` и cleanup'ы идут от
  последнего плагина к первому, как и положено ресурсам. Внутри одного плагина —
  тоже в обратном порядке регистрации.
- **`registry.unmount()` идёт до `view.unmount()`**, чтобы cleanup плагина ещё
  застал живое дерево. Повторный `unmount()` хуки не продублирует.
- **Ошибка в хуке жизненного цикла изолирована** — логируется, остальные хуки
  отрабатывают.

### Доступ из компонентов

Контекст плагинов кладётся в корневой `ContextType` и наследуется вниз по
цепочке (`createContext` копирует ссылку от родителя). Отсюда — четыре хелпера,
все работают только в `setup`:

| Функция | Поведение |
|---|---|
| `usePlugins()` | весь контекст; вне `setup` — warn и `{}` |
| `usePlugin(key)` | одно значение; вне `setup` — warn и `undefined` |
| `requirePlugin(key)` | то же, но бросает, если плагина нет |
| `hasPlugin(key)` | тихая проверка, без warn и без броска |

### Типизация

Свои плагины описываются через declaration merging — тогда `usePlugin("$router")`
вернёт нормальный тип, а не `unknown`:

```ts
declare module "orve" {
  interface OrvePlugins {
    $router: Router;
  }
}
```

`PluginContext = OrvePlugins & Record<string, unknown>` — объявленные плагины
типизированы, остальные доступны как `unknown`.

Файлы: `plugins/types.ts` (контракт), `plugins/plugins.ts` (`OrvePlugin` —
изоляция одного плагина), `plugins/registry.ts` (`PluginRegistry` — порядок,
дедупликация, жизненный цикл), `plugins/usePlugins.ts` (доступ из компонентов).

## 5. Рантайм (`src/runtime`)

### JSX-фабрика

`jsx(type, props, key)` возвращает плоский объект и ничего не вычисляет:

```ts
type VNode = { __orve: true; type: string | ComponentFn | FRAGMENT; props; key };
type Child = VNode | string | number | boolean | null | undefined | Slot | Child[];
type Slot = State | Computed | (() => Child);
```

Подключение у потребителя: `tsconfig.jsxImportSource: "orve"` — и всё, дальше
работает `exports`-карта пакета (`./jsx-runtime`, `./jsx-dev-runtime`).
Своего babel-плагина нет и не требуется. Внутри репозитория тот же импорт
заворачивается на исходники (`paths`, `moduleNameMapper`, vite-алиасы), чтобы
не собирать `dist/` ради dev и тестов.

### Представления (View)

```ts
interface View {
  key: Key;
  mount(parent: Node, anchor: Node | null): void;
  update(next: Child): boolean;   // false = несовместим, нужна замена
  unmount(): void;
  nodes(): Node[];                // все узлы верхнего уровня, для перемещений
  first(): Node | null;
}
```

| View | За что отвечает |
|---|---|
| `TextView` | текстовый узел; `null`/`undefined`/`boolean` → пустой текст |
| `ElementView` | тег, пропсы, дети; держит эффекты реактивных атрибутов |
| `FragmentView` | несколько узлов + замыкающий комментарий-якорь |
| `DynamicView` | реактивный слот: эффект читает сигнал/тонк и патчит поддерево |
| `ComponentView` | экземпляр компонента: scope, `ReactiveProps`, ветка режима |

Каждый View владеет своей `EffectScope`, но создаёт её лениво: работа идёт через
`runScoped()`, и пока внутри не появился эффект или вложенная область, View сам
выступает «владельцем» (`ScopeHost`) и ничего не аллоцирует. Текстовые узлы и
статические элементы так и живут без области. В конструкторе запоминается
родительский владелец, поэтому материализованная позже область встаёт ровно в ту
же ветку — цепочка родителей достраивается в момент, когда область впервые
понадобилась. `unmount()` гасит ветку.

### DOM-слой (`runtime/dom.ts`, `runtime/namespace.ts`)

Одно место, где решается «свойство или атрибут»:

| Проп | Как применяется |
|---|---|
| `class`, `className` | `normalizeClass`: строка, массив (falsy отбрасывается), объект `{ имя: условие }` → атрибут `class`; пустая строка снимает атрибут |
| `style` | строка целиком либо объект с подиффом по ключам: camelCase → `kebab-case`, `--custom` как есть, исчезнувшие ключи снимаются |
| `value`, `checked`, `selected`, `muted`, `innerHTML`, `textContent` | DOM-**свойство** (атрибут задал бы лишь начальное значение); `value` не переписывается, если там уже то же самое |
| `disabled`, `hidden`, `required`, `open`, … | атрибуты-флаги: `true` → пустая строка, `false`/`null` → снятие |
| `className` → `class`, `htmlFor` → `for`, `readOnly` → `readonly`, `tabIndex` → `tabindex` | переименование |
| `on*` | слушатель; суффикс `Capture` → фаза перехвата; кортеж `[fn, options]` → опции; снимается при замене и при размонтировании |
| `ref` | не атрибут: функция или сигнал получает узел, при размонтировании — `null` |
| прочее | `setAttribute`, `null`/`undefined`/`false` → `removeAttribute` |

**Пространства имён.** `<svg>` и `<math>` открывают своё пространство, дети его
наследуют, внутри `foreignObject` снова HTML. В SVG всё идёт через
`setAttribute` (там нет DOM-свойств, а `className` вообще только для чтения), и
регистр camelCase-атрибутов вроде `viewBox` сохраняется.

Текущее пространство лежит в модульной переменной (`getNS`/`withNS`), а не
тащится через каждую сигнатуру. Представления, которые досоздают детей позже
(`Dynamic`, `Fragment`, `Component`), фиксируют его в конструкторе и
восстанавливают при отложенном монтировании — иначе узел, появившийся внутри
`<svg>` по условию, создался бы как HTML.

### Реконсилятор

`patch(view, next, parent, anchor)` — обновить на месте или заменить.
`patchChildren` сопоставляет списки: узлы с `key` — по ключу, остальные — по
позиции; порядок доводится проходом с конца, двигаются только узлы не на месте.

Один и тот же реконсилятор работает и в базовом режиме (всё дерево компонента),
и в сингле (внутри отдельного `DynamicView`). Разница режимов сводится к тому,
**где стоит эффект**: вокруг всего render или вокруг каждого слота.

`createView` в [`mount.ts`](src/runtime/mount.ts) — единая точка разбора `Child`
в представление. При обнаружении слота (`State`, `Computed` или функции-тонка):

- **сингл** (`ctx.options.single === true`) — создаётся `DynamicView` с
  собственным эффектом: реактивность точечная, render не перезапускается.
- **base** (контекст есть, но `single` не установлен) — выводится
  `console.warn("[orve] Сигнал передан как слот в базовом компоненте …")`,
  слот читается через `readSlot` и рекурсивно разворачивается через `createView`:
  значение попадает в `TextView` или `ElementView` и участвует в render-эффекте
  компонента как обычное чтение.
- **вне компонента** (нет контекста) — создаётся `DynamicView` без предупреждения
  (применяется при монтировании корневого узла или в тестах напрямую).

### Встроенные компоненты

```tsx
<If when={signal} then={() => <b/>} else={() => <i/>} />
<For each={signal} by={(t) => t.id}>{(item, i) => <li>{() => item.value}</li>}</For>
<Component is={target} text={value}>дети тоже уезжают внутрь</Component>
```

Все три — сингл-компоненты, возвращающие тонк: их содержимое живёт в реактивном
слоте, поэтому пересобирается только затронутый участок дерева.

- `If.when` и `For.each` принимают значение, сигнал или тонк (`resolve()`).
- `For` держит строки: колбэк вызывается **один раз за жизнь строки** и получает
  `item` и `index` сигналами. Изменение массива не пересобирает уцелевшие строки —
  им только пишется новое значение в сигнал, и обновляется ровно та часть DOM,
  которая это значение читает. Подробнее — ниже.
- `Component` рендерит то, что лежит в `is`, а всё остальное, включая
  `children`, пробрасывает внутрь через `forwardProps(props, ["is"])`.
  Сменился `is` — старое поддерево
  размонтируется со своей областью эффектов, новое встаёт на место; `is` тот же,
  изменились пропы — `setup` не перезапускается, обновляются только ячейки
  пропсов.

  **Базовая форма — компонент, а не разметка.** Тогда пропсы объявляются там,
  где они реально появляются, — на `<Component/>`:

  ```tsx
  const current = computed(() => (page.value === 1 ? Basic : Single));

  <Component is={current.value} user={user.value} />
  ```

  `is` принимает также имя тега (`is="section"`) и уже готовый узел
  (`is={<Card />}`) — для узла пропсы с `Component` дорисовываются поверх его
  собственных. Но узел вынуждает объявлять пропсы внутри `computed`, до того
  как они известны, поэтому это запасной вариант. А если пропсы прокидывать
  вообще не нужно, `Component` не нужен тоже: узел — обычный `Child`, его
  кладут прямо в слот (`{current.value}` в базовом, `{current}` в сингле).

**`Component.is` не принимает тонк**, в отличие от `If.when` и `For.each`:
компонент сам является функцией, и `is={Card}` неотличимо от `is={() => Card}`.
Для вычисляемого выбора — `is={computed(() => flag.value ? A : B)}`. Это тот же
класс неоднозначности, что и у `State.set(fn)`, где функция всегда трактуется
как апдейтер.

Типизировать пробрасываемые пропсы по цели нельзя — она динамическая, поэтому у
`ComponentProps` индексная сигнатура, и проверка пропсов на `Component` не
работает.

### `For`: сигналы на строку

Колбэк строки вызывается один раз, при её появлении, и получает `State<T>` и
`State<number>`. Всё, что в строке зависит от данных, читает их через тонк:

```tsx
<For each={todos} by={(todo: Todo) => todo.id}>
  {(todo: State<Todo>) => (
    <div style={() => `font-weight: ${todo.value.done ? "bold" : "normal"}`}>
      {() => todo.value.name}
    </div>
  )}
</For>
```

Что происходит при изменении массива:

1. Тонк `For` перевызывается — это его зависимость от `each`.
2. Для каждого элемента считается идентификатор: `by(item, index)`, а без `by` —
   сама ссылка на `item`.
3. Уцелевшая строка находится в кэше по идентификатору: её `item`/`index`
   получают новое значение через `set`. Колбэк не вызывается, VNode не строится,
   `patchChildren` видит **ту же самую ссылку** на узел и не диффит пропсы.
4. Новый идентификатор — только тогда вызывается колбэк и строится строка.
   Исчезнувший — строка размонтируется вместе со своей областью эффектов.

Корень строки помечается собственным ключом (`orve:row:N`) — реконсилятор двигает
строку целиком. Свой `key` на узле внутри `For` не нужен, он перетирается: `For`
владеет идентичностью строк. Если строка вернула не узел (массив, тонк,
примитив), она заворачивается во фрагмент — носитель ключа.

**`by` называется не `key`**, потому что `key` зарезервирован JSX-рантаймом:
трансформ вынимает его из пропсов в `vnode.key`, и до компонента он не доходит.

Два следствия, о которых надо знать:

- **Без `by` идентичность строки — ссылка на `item`.** Иммутабельное обновление
  (`list.map(t => ({ ...t }))`) даёт новые объекты, поэтому строки пересоздаются
  и весь выигрыш пропадает. Для списков объектов `by` практически обязателен.
- **Мутация `item` на месте больше не видна.** Раньше она долетала до DOM, потому
  что колбэк перевызывался и VNode пересобирался. Теперь `set` сравнивает по
  `Object.is`, тот же объект не считается изменением. Обновлять надо заменой:
  `copy[i] = { ...copy[i], state: "done" }`.

Идентичная ссылка на VNode коротко замыкает `update` в `ElementView` и
`ComponentView` (`next === this.vnode` → `true`), поэтому переиспользование
строки не стоит почти ничего.

### Точка входа

```ts
createInstance().rootComponent(App).mountRoot("#app");
instance.unmount();
```

## 8. Пакет и сборка

Пакет называется `orve`, собирается в ESM (`"type": "module"`, `tsc` → `dist/`),
относительные импорты в `src/` пишутся с расширением `.js` — как требует
ESM-резолвинг Node и `moduleResolution: nodenext`.

`exports`-карта отдаёт три входа: `orve`, `orve/jsx-runtime`,
`orve/jsx-dev-runtime` — каждый с `types` и рантайм-файлом. Стороннему проекту
достаточно поставить пакет и указать `jsxImportSource: "orve"`; алиасы в его
конфигах не нужны — проверено на `tsc` с `nodenext` и `bundler`, `vite build`
и импорте из Node ESM.

Алиасы остаются только внутри репозитория и ведут на `src/`:
`paths` (tsconfig), `moduleNameMapper` (jest), `resolve.alias` (vite). Jest
дополнительно снимает `.js` с относительных импортов (`^(\.{1,2}/.*)\.js$`),
потому что на диске лежат `.ts`, и компилирует тесты в CJS — сам раннер не ESM.

## 10. Соглашения

- Пропсы читаются только через `props.x` — см. предупреждение в разделе 2.
  В примерах и в `playground/` этот стиль соблюдается везде: любой `({ x })`
  в сигнатуре компонента считается ошибкой ревью.
- Комментарии и сообщения об ошибках — по-русски, префикс `[orve]`.
- Тесты — jest + ts-jest + jsdom, описания по-русски, рядом в `__tests__`.
- Реактивные чтения внутри DOM-работы всегда оборачиваются в `untrack`:
  эффект должен зависеть от данных, а не от побочных чтений при патче.
